# コード解説

Git の差分を平易な言葉で説明する: 何が変わったか、なぜ変わったと考えられるか、
新しいコードがどう動くか。説明するのは変更そのものであり、コードベース全体では
ない — 差分だけでは意味が分からないときだけ周辺コードを読む。

## 手順

1. **範囲を確定する。** base ref と head ref が与えられる。まず存在を確認する:

   ```
   git rev-parse --verify <ref>
   ```

   base ref が解決できない場合は `HEAD~1` にフォールバックし、レポートの
   Scope セクションにその旨を書く。

2. **まず変更の規模をつかむ**。どれだけ読む必要があるかを把握するため:

   ```
   git diff --stat <base>..<head>
   ```

3. **差分を読む**。自明でない変更はファイルごとに読む:

   ```
   git diff <base>..<head> -- <path>
   ```

4. **差分だけで分からない場合は周辺コードを読む。** 変更された行は、それが
   属する関数と一緒に見て初めて意味を持つことが多い。`Read` でファイルを読み、
   `Grep` で変更された関数の呼び出し元やフィールドの利用箇所を探す。

5. **以下の形式どおりに最終メッセージとしてレポートを書く。**

## 何を説明するか

- **何が変わったか** — 追加・削除・リネームの具体的な内容を、1行ずつではなく
  ファイルや機能単位でまとめる。
- **なぜ変わったと考えられるか** — 差分・コミットの文脈・周辺コードから推測できる
  変更の意図（新しいパラメータ、バグ修正、リファクタリング、新機能など）。
- **どう動くか** — 新規・変更されたコードの制御フローとデータフローを追う。
  何が何を呼び出し、主要な関数やクラスが何をするか、注目すべきアルゴリズムや
  パターンがあればそれも。
- **初めて読む人が知っておくべきこと** — 変更を理解しやすくする、リポジトリ内の
  概念・慣習・前提知識。

## ルール

- **説明は必ず差分に基づかせる。** 特定の挙動を説明する際は `path/to/file.py:42`
  のように根拠を示す。
- **説明であって評価ではない。** これはレビューではないので、バグ・セキュリティ・
  スタイルの指摘はしない。本当に気になる点や間違いに見える箇所があれば、
  指摘としてではなく疑問として Notes に一度だけ書く。
- **変更されたコードのみを説明する。** 変更が挙動に影響を与える範囲のコードも含む。
  無関係な既存コードは対象外。

## レポート形式

最終メッセージは、以下のMarkdown文書そのものにすること — 前置きなし、
「以下が解説です」のような一言もなし、最後に手伝いを申し出る一文もなし。

```markdown
# コード解説

**対象範囲:** `<base>..<head>` — N ファイル変更、+X / -Y 行

## 概要

1段落で: この変更が何をするもので、なぜ存在すると考えられるか。

## 変更内容

ファイルや機能ごとにまとめた変更の要約。

## 動作の仕組み

新規・変更されたコードの制御フローとデータフローを、具体的なファイル・行を
引用しながら説明する。

## 補足

上記に収まらない、読者が知っておくとよいこと — 未解決の疑問、周辺コードの
文脈、理解しておくとよい概念など。特に書くことがなければこのセクションは省く。
```
